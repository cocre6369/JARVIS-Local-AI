# Packaging JARVIS for Windows

JARVIS ships as a normal Windows program: one installer a person can
double-click, a desktop shortcut, an entry in *Add or remove programs*.
Nothing in the build needs the user to open a terminal, install Python, or
touch the source tree.

## What gets built

| Artefact | What it is |
| --- | --- |
| `dist/JARVIS/JARVIS.exe` | The application (PyInstaller **onedir**). Fast start, no self-extraction, kinder to antivirus. |
| `dist/JARVIS-Setup-<version>.exe` | Inno Setup installer: per-user install to `%LOCALAPPDATA%\JARVIS`, desktop shortcut, clean uninstaller. No admin rights needed. |
| `dist/JARVIS-portable-<version>.zip` | The same folder zipped, for people who prefer a portable copy. |
| `packaging/assets/jarvis.ico` | Generated by `make_icon.py` (pure standard library - the same arc-reactor art the UI draws). Regenerated on every build; do not hand-edit. |

## Build on your own machine

```powershell
powershell -ExecutionPolicy Bypass -File packaging\build_windows.ps1
```

The script creates a clean venv under `.build/`, installs `requirements.txt`
plus PyInstaller, draws the icon, runs `jarvis doctor` as a smoke test, freezes
the app with `packaging/jarvis.spec`, and - if Inno Setup 6 is installed -
compiles the installer. Without Inno Setup it stops after the freeze; the
`dist\JARVIS` folder is then already a complete, runnable install you can copy
anywhere.

## Build in CI (the supported path)

`.github/workflows/build-windows.yml` runs on `windows-latest`:

1. installs dependencies and PyInstaller;
2. regenerates the icon;
3. compiles everything, boots the engine headless (`jarvis doctor`), runs pytest;
4. freezes with the same spec file;
5. **runs the frozen exe** (`JARVIS.exe version` and `doctor`) so a bad freeze
   fails the build instead of reaching a user;
6. builds the Inno Setup installer and a portable zip;
7. uploads both as workflow artefacts, and - for `v*` tags - attaches them to a
   GitHub Release so users download them from the Releases page.

## Why onedir and not a single file

A `--onefile` build writes itself to `%TEMP%` and unpacks hundreds of
megabytes on *every* launch, which costs several seconds and makes Windows
Defender suspicious of an unknown binary. A folder plus an installer gives a
sub-second start and a familiar install experience, which is what a
non-technical user actually needs.

## What is deliberately NOT in the bundle

* **No large language model.** Ollama and its models stay in Ollama's own
  folder; bundling a 4-8 GB model into an installer would be hostile. The
  first-run wizard detects Ollama, and if it is missing it says exactly where
  to get it and what to pull.
* **No cloud anything.** The frozen app contains no OpenAI/Azure/Google
  client code and no telemetry endpoint - the security layer refuses outbound
  uploads at runtime, and `security.netguard` fails closed.
* **UPX is off.** Compressing the executable is the single most common trigger
  for false-positive antivirus flags.

## Single instance

`jarvis/app.py` holds a named mutex (`jarvis-single-instance`) on Windows, so a
second launch focuses the running window instead of starting a competing
runtime. The installer checks the same mutex and offers to close JARVIS before
overwriting files.

## Data, settings and logs

Everything JARVIS writes lives in `%LOCALAPPDATA%\JARVIS-data` (override with
`JARVIS_DATA_DIR`): `settings.json`, `memory/jarvis.db`, `security/audit.db`,
`logs/`, and disposable `scratch/` screenshots. Uninstalling the app leaves
memories and settings in place; deleting that folder is a full reset.
